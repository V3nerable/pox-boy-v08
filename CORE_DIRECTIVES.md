# CORE AI DIRECTIVES
**These instructions must be acknowledged and adhered to before executing ANY command.**

1. **Acknowledge Directives:** Start every response by confirming these directives have been read and noted.
2. **Discussion Mode Default:** Treat all user prompts as discussion/brainstorming ONLY. Do not write, edit, or modify any code files unless the user issues a clear deploy command (the exact phrase **"deploy this"**, or obvious equivalents such as "deploy", "deploy all", "lets deploy"). **POSTPONE RULE:** When a deploy is commanded, default to deploying exactly what is presented — BUT if you have a materially better UX/UI suggestion or idea based on what is presented, postpone the deploy and discuss the suggestion first instead.
3. **Strict Versioning:** If "deploy this" is commanded, increment the application version number by exactly `0.01` across all relevant files (`index.html`, Zip name, etc) before pushing changes. **CRUCIAL:** You must use `sed` or explicitly edit `index.html` to find and replace the hardcoded "v0.XX" text tags visible on the UI so the screen matches the zip file!
4. **Handoff Readiness:** Upon every successful deployment, update the master Zip file (`Pox-Boy-3026-v0.XX.zip`) containing the full `pwa/` directory (including `AGENT_HANDOFF_INSTRUCTIONS.md`) so the project is perfectly prepped for another agent to take over if the context window drops.
5. **No Native Popups:** Never use standard browser `alert()` or `confirm()`. All warnings/prompts must be routed through the custom in-app `showNotification()` or `showCustomPrompt()` functions to maintain immersion.
6. **No Native Keyboards:** Ensure all new `<input>` or `<textarea>` elements are tagged with `class="pip-input vk-target" readonly onclick="openVk('element-id')"` to enforce the use of the in-app glowing virtual keyboard.
7. **Offline-First PWA:** Do not attempt to migrate data to a cloud backend (unless updating the specific Firebase GPS radar). All core data must continue saving to `localStorage`.
8. **Cache Management:** Remember to bump the `CACHE_NAME` in `sw.js` during any deployment so attendees' phones download the newest files.
9. **Deployment Report:** After actioning any deployment, the report structure is strictly: (1) DETAILED point-by-point breakdown of every change; (2) **DEPLOY STEPS** — a concise, numbered checklist of the user's manual actions to ship the build, in order (e.g. *only when flagged:* paste updated Firebase rules into the console → Publish; download & unzip the new zip; drop the files onto the GitHub repo root; commit & push; Netlify auto-publishes; hard-refresh / delete old home-screen icon & reinstall when the manifest or icons changed; verify version tag on screen). Include ONLY the steps that apply to that release — skip the Firebase step when rules are untouched. (3) TL;DR — each individual change summarised in exactly ONE plain-language sentence (one line per item, no jargon). `AGENT_HANDOFF_INSTRUCTIONS.md` remains the long-term source of truth; its per-version changelog stays technical.
10. **Version Enforcement:** Before ANY deployment, verify and increment the version number by exactly `0.01` regardless of change size. Check current version in `index.html` (search for `v0.XX` tags), bump to next version, update `CACHE_NAME` in `sw.js` to match (e.g., v0.64 → pipboy-cache-v53), and ensure the zip filename matches the new version. Never deploy without version increment — even single-line fixes require +0.01.
